## 2026-11-11 — feat(app): недельная система РК — среднее недельных средних, как у тулзы

**Что.** `computeCourseGrades` переведён на модель официального тулзы:
1. работы группируются в недели по календарной неделе дедлайна (предыдущий
   фикс);
2. **НЕДЕЛЯ = среднее процентов работ этой недели** (нули считаются);
3. **РК1 = среднее недельных средних недель 1–8**, РК2 = недель 9–15
   (а не среднее всех работ периода, как было);
4. работы без даты и номера — одна синтетическая «неделя» на РК (их среднее
   участвует как один элемент), распределение по id-порядку сохранено;
   `itemsRk1/itemsRk2` — прежние счётчики работ (подписи «Ср.тек. 1 · N»).

**Почему.** Юзер открыл модалку Платонуса INOPAK и увидел, что «оценки по
дням» теперь содержат НЕДЕЛЬНЫЕ средние по понедельникам (Авг 31 = 83 ≈
Неделя 1 = 82.50, Сен 7 = 50 = Неделя 2…): тулза считает средний балл каждой
учебной недели и передаёт его в Платонус, а РК1/РК2 считает как среднее
недельных средних. Проверка точной арифметикой на данных INOPAK:
РК1 = mean(82.5, 50, 50, 81.67, 77.5, 81.5, 87.5, 85.67) = **74.54** ✓,
РК2 = mean(88.5, 100) = **94.25** ✓, Рейтинг = **84.40** ✓ — совпадает с
тулзой и журналом до сотой. Прежняя модель «среднее всех работ периода»
давала 75.56/92.33.

**Файлы.** `src/lib/grade-scheme.ts` (агрегация meanOfWeeks + синтетическая
неделя для недатированных), `CONTEXT.md` (раздел «Формула оценок» — новая
недельная система).

**Для Tauri.** Формула портится как есть: неделя = среднее работ недели по
календарной неделе дедлайна; РК = среднее недельных средних; Рейтинг =
(РК1+РК2)/2; Итог = round(0.6×Рейтинг+0.4×Экз).

## 2026-11-11 — fix(app): РК-группировка по календарной неделе дедлайна, а не по №N в названии

**Что.** `computeCourseGrades`: неделя работы теперь определяется сначала по
КАЛЕНДАРНОЙ неделе эффективного дедлайна (due_at, а без него lock_at — через
`getAcademicWeek` от якоря семестра), и только если даты нет — по номеру из
названия («Тест №3» → 3-апта). Недели 1–8 = РК1, 9–15 = РК2, как раньше.
Без даты и номера — прежние фолбэки (дата против границы / ID-порядок).
Лейблы «N-апта» в AI-контексте (`aiContext.ts`) — та же логика.

**Почему.** Юзер заметил: «БӨЖ №1» (INOPAK) со Сроком 27.09 и в модуле
«Неделя 4» попадал у нас в неделю 1 — номер в названии («первое БӨЖ») не
равен учебной неделе. Официальный LTI-тул группирует по датам (Неделя 4 =
Тест №4 + Практика №4 + БӨЖ №1), его РК уходят в Платонус. Свёрка на
данных тулзы: все 11 видимых дедлайнов INOPAK ложатся в те же «Неделя N»
(06.09→1 … 11.10→6, БӨЖ №1 27.09→4). Прежний приоритет «название → дата»
давал систематический сдвиг РК-состава и расхождение вычисленных цифр
с официальными (INOPAK: ≈83.95 против 84.40).

**Файлы.** `src/lib/grade-scheme.ts` (`weekOf`: дата → название), `src/lib/aiContext.ts`, `CONTEXT.md` (раздел «Формула оценок» переписан).

**Для Tauri.** Группировка — чистая функция; в порту сохранить приоритет
«календарная неделя дедлайна → номер из названия».

## 2026-11-11 — fix(app): рейтинг допуска из Платонуса — официальные числа вместо вычисленных

**Что.** Приоритет источников рейтинга курса стал трёхступенчатым:
`courseAdmissionRating()` (новый хелпер в `grade-scheme.ts`):
1. **canvas** — официальный итог Canvas (если грейдбук снова начнут считать);
2. **platonus** — «Рейтинг» из журнала Платонуса (запись с максимальным
   годом/термином, содержащая код курса, напр. «INOPAK 111252-1-L»);
3. **computed** — вычисленный из тапсырм (прошлый фолбэк, остаётся последним).
Полоска «Оценки Canvas» и карточка предмета: Платонус-число показывается
БЕЗ «≈» и курсива (оно официальное) с тултипом `canvasPlatonusScoreHint`;
подпись в карточке предмета меняется на «Рейтинг».

**Почему.** Юзер сверил с тулзой: наша вычисленная цифра расходится
(INOPAK: ≈83.95 против официального Рейтинг допуска 84.40) — тулза
агрегирует по неделям от ДАТ сдачи, наша схема по №N в названии
(«БӨЖ №1» со сдачей в неделе 4 у нас в неделе 1). Реверсить тулзу не
потребовалось: тулза пишет официальные РК в Платонус («передано в
Platonus»), а журнал Платонуса расширение уже синкнит — официальные
числа просто лежат в `platonusYears[].subjects[].rating`.

**Миграция юзера.** Пересинкнуть Платонус (последний синк был до
очередной передачи тулзы) — журнал подтянет свежие РК.

**Файлы.** `src/lib/grade-scheme.ts` (хелпер), `src/pages/DeadlinesPage.tsx`,
`src/components/deadlines/CanvasGradesStrip.tsx`,
`src/components/subjects/CanvasGradesCard.tsx`, `src/i18n/{kk,ru}.ts`
(ключ `canvasPlatonusScoreHint`).

**Для Tauri.** Хелпер — чистая функция, переносится как есть. Сортировка
«новейшая запись» — по year, затем term.

## 2026-11-11 — fix(app): «≈рейтинг» из тапсырм — Canvas больше не отдаёт итоги (вуз перенёс оценки в LTI-тул)

**Причина пропажи баллов найдена.** Вуз вынес оценки из штатного Canvas
грейдбука в свой LTI external tool (страница «Оценки» курса теперь
`canvas.yu.edu.kz/courses/{id}/external_tools/1`: РК1/РК2/Рейтинг допуска +
подытоги по неделям, «Обновлено … передано в Platonus»). Canvas грейдбук
итогов больше не хранит → `/users/self/enrollments?include[]=total_scores`
и `courses?include[]=total_scores` оба отдают 200 без `grades.current_score`
→ синк работал, но все курсы приходили с `null`, полоска «Оценки Canvas»
показывала «—». Расширение при этом ни при чём — тапсырмы, сдачи и их баллы
API по-прежнему отдаёт.

**Что сделано (в приложении).** Когда `current_score === null`, полоска
«Оценки Canvas» (DeadlinesPage: мобильная горизонтальная + десктопная
вертикальная) и карточка «Canvas бағалары» на странице предмета показывают
**«≈рейтинг»**, вычисленный из уже засинкнутых тапсырм по той же схеме, что
и LTI-тул: `computeCourseGrades(course, assignments, semester).rating`
(РК1 = недели 1–8, РК2 = 9–15, Рейтинг = (РК1+РК2)/2). Отличия: «≈» перед
числом, курсив, тултип с объяснением (`canvasComputedScoreHint`). Если
Canvas когда-нибудь снова начнёт отдавать официальный итог — он приоритетен.

**Проверка схемы на данных тулзы (INOPAK 111252-1-L):** Неделя 1 = среднее
элементов недели (100 и 65 → 82.50 ✓), Рейтинг допуска = (РК1+РК2)/2
(74.54+94.25 → 84.40 ✓) — совпадает со схемой приложения.

**Файлы.** `src/components/deadlines/CanvasGradesStrip.tsx` (проп `ratings`,
≈/курсив/тултип), `src/pages/DeadlinesPage.tsx` (`courseRatings` через
`computeCourseGrades`), `src/components/subjects/CanvasGradesCard.tsx`
(тот же фолбэк), `src/i18n/kk.ts` + `ru.ts` (ключ `canvasComputedScoreHint`).

**Дальше (опционально).** Официальные числа тулзы можно синкать напрямую:
страница тулзы — серверный HTML во фрейме внешнего домена; нужен дамп этой
страницы (аналог `platonus-dump-sample.html`) — тогда расширение сможет
фетчить тулзу и парсить РК/недельные подытоги как источник «официальных»
баллов. Пока не начато — ждёт дамп от юзера.

**Для Tauri.** Фолбэк-вычисление рейтинга живёт в `grade-scheme` (чистая
функция) — в порту переиспользуется как есть; официальные числа тулзы, если
будут синкаться, кладутся в то же поле `current_score` с пометкой источника.

## 2026-11-11 — fix(canvas): диагностика потери баллов + явный include[]=enrollments

**Что.** После ретраев (`ddf053a`) у юзера баллы всё равно не доехали — то есть
enrollments-запрос падает стабильно, не транзиентно. Добавлено:
1. `fetchGradeMap` возвращает не только map, но и `diag` — строку-причину
   («200 без оценок ×3» или сообщение ошибки, напр. «Canvas API 403 для
   /api/v1/users/self/enrollments»). Диагноз показывается в попапе:
   «… · балдар жүктелмеді — Canvas-синкті қайтала [причина]», и в `lastResult`
   переоткрытого попапа: «(⚠ баллы: причина)».
2. Запрос курсов теперь явно просит `include[]=enrollments` ( grades живут в
   `c.enrollments[0].grades`; раньше полагались на Canvas, который отдавал
   enrollments неявно при `include[]=total_scores` — если Canvas изменил это
   неявное поведение, оба источника разом опустели бы, что и наблюдается).
3. `gradesDiag` кладётся в payload (валидатор дашборда игнорирует
   неизвестные поля, в сторы не пишется — только для попапа).

**Почему.** Причина пропажи баллов неизвестна — мог заблокировать Canvas
(403), могло измениться неявное поведение include. Гадать нельзя: диагноз
попадает в глаза юзеру, чиним по факту.

**Файлы.** `extension/background.js`, `extension/popup.js`,
`userscript/aristos-sync.user.js`.

**Ожидаемый исход.** Юзер перезагружает расширение → синк → в попапе видно
причину: «403» — Canvas запретил эндпоинт (обсуждать альтернативный источник
баллов, напр. per-course enrollments); «200 без оценок ×3» — форма ответа
изменилась, смотреть дамп ответа в консоли service worker; «Сессия Canvas
истекла» — перезайти в Canvas.

**Для Tauri.** Та же схема: диагноз причины неудачи «мягкого» запроса должен
доходить до UI, не только в лог.

## 2026-11-11 — fix(canvas): оценки курсов пропадали молча — ретраи enrollments + предупреждение в попапе

**Что.** В Canvas-синке запрос баллов курсов
(`/api/v1/users/self/enrollments?include[]=total_scores`) сделан упорным:
до 3 попыток с паузой 1.5с/3с — как при ошибке запроса (401/403/сеть), так и
при «успешной пустышке» (200 без `grades`). После исчерпания ретраев синк
дальше идёт как раньше, но попап теперь показывает: «Синктелді: N курс, M
тапсырма · балдар жүктелмеді — Canvas-синкті қайтала» (и «⚠ баллы» в
`lastResult` для переоткрытого попапа). То же в userscript.

**Почему.** Запрос баллов — «мягкий» по дизайну: его падение не валит синк,
курсы и тапсырмы продолжают грузиться, но `current_score` у всех курсов
становился `null` и полоска «Оценки Canvas» показывала «—» вместо процентов
(92.05% и т.п.) — молча, без единого признака сбоя в UI. У юзера так
произошло в синке 11.11 02:44 (после переустановки расширения; похоже на
разовый сбой запроса — VPN/прокси/Canvas). Ретраи снимают транзиентные
падения, предупреждение делает остаточный случай видимым.

## 2026-11-11 — fix(extension): ошибки воркера в попапе локализуются (KK/RU)

**Что.** Ошибка в попапе раньше всегда показывалась по-русски («Қате: Не
удалось определить studentID…»), хотя язык попапа казахский. Теперь попап
узнаёт знакомые ошибки воркера по шаблонам (`ERROR_MATCHERS`) и показывает их
на выбранном языке; незнакомые строки (сырые сетевые сбои, текст валидации
приложения) проходят как есть. Префиксы «Қате: / Ошибка:» уже были
локализованы, дело было в теле сообщения.

**Почему.** Стадии прогресса переводились через протокол `stageKey`
(воркер передаёт ключ, попап рендерит по `I18N`), но брошенные исключения
(`throw new Error('…')` в `background.js`) — готовые русские строки: у
service worker нет контекста языка попапа. Менять воркер (код + передача
языка в storage.session) инвазивно — перевод решён на стороне попапа, где
язык и так есть.

**Файлы.** `extension/popup.js` — 17 ключей `err*` в KK и RU, таблица
`ERROR_MATCHERS` (regex → ключ → параметры), `localizeError()`, применена в
4 местах: ветка `error`, ветка `export` (внутреннее сообщение), ветка
`lastError` в `pollSyncState` и в `init` (переоткрытый попап читает
`syncState.lastError` из storage.session — теперь тоже переводится).

**Контракт.** При изменении текста ошибки в `background.js` синхронно
правится regex в `ERROR_MATCHERS` (комментарий-напоминание в коде). Проверка
покрытия: все известные сообщения воркера матчатся (прогнано скриптом).

**Для Tauri.** В порту ошибки поднимаются из нативных команд — сразу
формировать с ключом/кодом (не сырой строкой), чтобы не тащить эту
regex-таблицу: `errCode` + параметры, локализация на фронте.

## 2026-11-11 — feat(canvas): «Доступно до» (lock_at) как дедлайн, когда Срока нет

**Что.** Canvas-синк теперь собирает и `lock_at` (поле «Доступно до» на странице
задания), а весь дедлайн-код дашборда перешёл на `effectiveDeadline()` —
`due_at ?? lock_at`. Правило: «Срок», а если не задан — «Доступно до».
Раньше такая работа попадала в «Без срока» с прочерком даты.

**Почему.** Часть работ (БОЖ/СОБЖ у CGNSH и т.п.) преподаватели не ставят
со сроком, но закрывают приём окном доступности: Canvas показывает
«Срок: не задан / Доступно: до 29 Ноя в 23:59». Для студента это тот же
дедлайн — дашборд молчал о нём до последнего дня. Из ~169 работ «без срока»
немалая часть — такие окна.

**Файлы.**
- `extension/background.js` + `userscript/aristos-sync.user.js` — в payload
  добавлено `lock_at: a.lock_at || null` (оба источника, канвас-эндпоинт
  отдаёт `lock_at` без доп. параметров).
- `src/types/index.ts` — `CanvasAssignment.lock_at: string | null`.
- `src/lib/canvas.ts` — валидатор принимает старые payload'ы без `lock_at`
  (опционально, обратная совместимость); новый `effectiveDeadline(a)`.
- Потребители дедлайнов, переведённые на `effectiveDeadline()`:
  `src/pages/DeadlinesPage.tsx` (карточка: акцент, дата, «Просрочено»;
  бакеты сегодня/неделя/позже/просрочено/без-срока и сортировки),
  `src/components/home/UpcomingDeadlines.tsx`,
  `src/components/charts/DeadlineBars.tsx` (недельные бары),
  `src/components/layout/NotificationAgent.tsx` (уведомления 48ч),
  `src/lib/aiContext.ts` (ближайшие дедлайны/просрочки в контексте AI),
  `src/components/ai/WeeklyAdviceCard.tsx` (ближайший дедлайн в совете),
  `src/lib/grade-scheme.ts` (РК1/РК2-разбивка по дате, фолбэк-граница).
- НЕ переведены (осознанно): лейблы дат оценённых работ
  (`GradesPage`, `CanvasGradesCard`, `GradeDynamics`) — там приоритет
  `submitted_at`, дата сдачи важнее окна доступности.

**Побочное поведение.** В `grade-scheme.computeCourseGrades` фолбэк-граница
РК1/РК2 (когда нет акад.календаря) теперь берётся как МЕДИАНА дат
(было: элемент в середине неотсортированного массива, а undated давали
эпоху-1970). Работы с одним только `lock_at` теперь тоже датируются для
РК-разбивки.

**Миграция.** Старые записи в `canvasAssignments` (IndexedDB) не содержат
`lock_at` — код это переживёт (`??`-цепочка), поле появится после первого же
Canvas-синка; валидатор его пропускает как опциональное. Переустановить
расширение (background.js поменялся).

**Для Tauri.** `effectiveDeadline` — единственная точка правила «Срок →
Доступно до»: в порту сохранить её (не размазывать `due_at ?? lock_at` по
компонентам). Payload-схема `{...version:1}` — поле добавлено, версия не
менялась: приемник обязан игнорировать незнакомые поля и валидировать
опционально.

## 2026-11-11 — fix(weeks): учебная неделя считается от понедельника недели старта семестра

**Что.** `getAcademicWeek` считал неделю строго от даты старта семестра
(`floor((сегодня − старт) / 7дн) + 1`). Теперь сначала сдвигается к понедельнику
недели, содержащей дату старта (`semesterWeekAnchor`), и недели считаются от
него. Новая экспортированная `weekStartDate(semesterStart, week)` возвращает
понедельник учебной недели N — ей теперь строит тултипы сетки недель
`SemesterTimeline.weekDateRange` (раньше там была своя арифметика от даты
старта + `toISOString`, который для отрицательных часовых поясов сдвигал
дату на день).

**Почему.** Пары живут по неделям Пн–Вс. Семестр 2026/27 стартует 01.09
(вторник), но пары идут с понедельника 31.08 — это видно и по журналу
Платонуса (первая оценка 31.08), и по акад.календарю (ориентация с 24.08).
Старая формула давала 09.11.2026 (понедельник) = неделя 10, хотя фактически
идёт неделя 11; заодно неделя 15 «вылезала» за конец семестра (старт 08.12,
конец 14.12 при семестре до 12.12). После фикса: 31.08–06.09 = неделя 1 …
07–13.12 = неделя 15 (конец семестра 12.12 внутри), 09.11 = неделя 11.

**Файлы.** `src/lib/academic-week.ts` (переписан: `localDay` — парсинг
«YYYY-MM-DD» в локальную полночь, `semesterWeekAnchor`, `weekStartDate`,
`getAcademicWeek` от якоря), `src/components/calendar/SemesterTimeline.tsx`
(тултипы через `weekStartDate`).

**Поведение.** Все вызовы (`status.ts` — «текущая неделя» и подбор тем,
`WeekProgress`, `HomePage`, `CalendarPage`, `SubjectDetailPage`,
`SemesterTimeline`) обновились автоматически — они передают только дату и
старт семестра. Дни до понедельника недели старта (ориентация 24–30.08)
по-прежнему показывают неделю 1.

**Для Tauri.** Чистые функции дат — переносить как есть; `localDay` обязателен
(не использовать `new Date(iso)`, это UTC-полночь). Проверено на реальных
датах: якорь 31.08, 09.11 → 11, 12.12 → 15.

## 2026-11-11 — fix(platonus): августовские оценки первого семестра получали год+1

**Что.** В парсере журнала Платонуса (`platonusCardExtract`) год даты оценки
выводится из выбранного в Платонусе учебного года («год: 2026» = учебный
2026/27). Правило было `month >= 9 ? year : year + 1` — все месяцы до сентября
(включая август) получали `year+1`. Стало `month >= 8 ? year : year + 1`:
август–декабрь → `year`, январь–июль → `year+1`.

**Почему.** В осеннем семестре пары начинаются в конце августа (в 2026/27 —
31.08, понедельник): Платонус показывает «Август 31 — 100» первым месяцем
модалки, а дашборд сортирует оценки по ISO-дате (`GradesPage.PlatonusMarksGrid`
— `[...items].sort(a.date.localeCompare)`). С датой `2027-08-31` «Август»
вставал **последним** месяцем сетки «Оценки по дням». Январь-сессия осеннего
семестра и декабрь весеннего по-прежнему разруливаются тем же правилом
(янв → year+1 ✓, дек → year ✓).

**Файлы.** `extension/platonus-inpage.js` (строка `const y = month >= 8 …`),
`tools/test-platonus-parser.mjs` (новая карточка 302 с таблицей «Август 31 /
Сентябрь 7» — проверка `['2026-08-31', '2026-09-07']` при year=2026).

**Миграция.** Уже засинкнутые записи `platonusYears` содержат неверные даты
(«2027-08-31») — после переустановки расширения нужен повторный Platonus-синк
(«Найти доступные периоды» → «Импорт выбранных»), `applyPlatonusSync`
заменяет записи целиком.

**Для Tauri.** Логика — чистая функция над DOM-модалкой; в порту переносится
как есть (если парсинг останется в webview-скрипте). Тесты парсера гонять той
же командой `node tools/test-platonus-parser.mjs`.
